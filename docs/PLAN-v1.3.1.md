## 1. 원목 줍기 멈춤

### 1.1 증상 — 사용자 실행 기록 **[측정]**

`data/runtime/logs/session_1793270237791.jsonl`(19:37 시작, 실제 모델 4개 · CUDA · `embedding` 인식기, seed 1 · 험지 · 바퀴). "원목 1개를 창고로 가져와" → 나무 n6을 캐서 원목 d7 · d8 · d9가 떨어진 직후, 단계 4 "원목 줍기"에서

```
원목: 포크 길 앞에 있는 원목(d9)부터 듦 — 뒤의 것(d7)에 포크를 밀어 넣지 않음
원목: 포크 길 앞에 있는 원목(d8)부터 듦 — 뒤의 것(d9)에 포크를 밀어 넣지 않음
원목: 포크 길 앞에 있는 원목(d9)부터 듦 — 뒤의 것(d8)에 포크를 밀어 넣지 않음

```

가 63.6 s 동안 1,259,018줄 이어졌다(파일 452 MB). 한 틱 안의 루프라 월드 잠금을 쥔 채 화면이 멈췄다.

### 1.2 원인

`driver.rs::do_collect`는 지게차일 때 대상보다 포크 길 앞에 있는 원목을 먼저 들도록 `fork_front_pick`이 고른 원목과 순서를 바꾸고(`swap`) 같은 틱에서 다시 판단한다(`continue`). 판정이 두 가지로 대칭을 깨지 못했다.

1. **"앞"의 정의**: 레인(반폭 0.30 m) 안에서 투영 거리가 대상보다 짧기만 하면 앞이었다. 쓰러진 나무는 원목을 줄기에서 0.13 m 둘레에 떨어뜨리므로(서로 약 0.22 m) 거의 같은 거리에 나란한 두 원목은 서로의 레인 안에서 서로보다 짧다 **[유도]**.
2. **위치의 출처**: 대상은 작업 기억(비전이 본 자리, 실제 모델이면 수 cm 오차)으로, 이웃은 실제 위치로 쟀다. 기억이 조금 먼 쪽으로 어긋나면 각 원목이 상대를 앞으로 본다. 오라클 인식기(개발 서버 · 시험)는 같은 seed에서 이 경로를 그대로 지나가도 멈추지 않았다 — 오차가 있어야 생기는 루프다.

`c73f363`(1 : 2 : 4)는 게임 통과의 줍기 판정을 바꾸지 않는다. 실제 모델로 처음 돌린 시점에 드러났을 뿐이다.

### 1.3 고침 (`crates/noto-runtime/src/driver.rs`)

- 앞 = 레인 안 + **두 원목 크기의 절반 합만큼 더 가깝다**(포크가 그것을 먼저 만남). 나란한 이웃은 앞이 아니며, 포크는 이웃을 비켜 들어갈 자리로 정렬한다(`fork_lineup`, 기존).
- 모든 원목의 위치를 **같은 출처**로: 작업 기억, 없으면 믿는 위치.
- 그래서 바꿀 때마다 대상까지 거리가 엄격히 줄어 원목 수보다 적게 바꾼다. 그래도 한 틱이 다시 돌지 않게 원목 수만큼으로 상한을 둔다.

## 3. 시계열 · SDS 정밀도

### 3.1 SDS 드리프트 (`noto-sds/src/stats.rs::drift_z`)

옛 식은 (링 평균 − 전체 평균) / 값 하나의 표준편차였다. 링이 전체 평균과 표준편차에 들어가 자기 쪽으로 끌고, 링 평균의 표준오차(σ/√k)를 무시했다. 새 식은 링과 그 앞 값들의 **두 표본 z**(합동 분산)다. 모델 · 몸이 바뀌어 보정이 옮겨 가는 것을 잡는 데 쓰인다(`calibration_factor`가 링 평균으로 다시 맞춤).

**[측정]** 40개 뒤 링 크기만큼 이동(2,000회), `drift_z > 문턱`인 비율:

| 링(트랙) | 옛 식 > 2: 0σ / 1σ / 2σ / 3σ | 새 식 > 3: 0σ / 1σ / 2σ / 3σ |
|---|---|---|
| 8 (vision · search) | 0 / 0 / 0 / 0 % | 0 / 36 / 98 / 100 % |
| 6 (depth · locate · tracker · fusion) | 0 / 0 / 0 / 14 % | 0 / 25 / 94 / 100 % |
| 4 (act · motion · decide · balance · memory · quest) | 0 / 0 / 9 / 62 % | 0 / 16 / 79 / 100 % |

보정을 링으로 다시 맞추는 문턱은 3으로 올렸다(`RECENTRE_Z`). 2면 안정된 산포가 20번에 한 번 값 몇 개로 다시 맞췄다(300회 중 10회가 15 % 넘게 빗나감).

### 3.2 보정 계수 (`store.rs::calibration_factor`)

깊이 배율 같은 비율은 곱셈으로 흩어진다. 비율의 산술 평균은 전형적인 비율보다 exp(σ²/2)만큼 크다(±30 %면 +4.6 %) **[유도]**. 중심을 기하 평균으로 바꿨다: 전체 이력은 모멘트로(로그 정규에서 정확, 평균 / √(1 + cv²)), 링은 값들의 로그 평균으로. 저장 형식은 그대로라 예전 원장을 그대로 읽는다.

**[측정]** ±30 % 로그 정규 비율 120개 × 300회(참값 1.000): 옛 1.044 ± 0.028 → 새 1.002 ± 0.034 (15 % 넘게 빗나간 실행 1회).

**[측정]** 400개 합성 계열(값 산포 0.05), p10–p90 띠가 다음 값을 담는 비율(명목 80 %):

띠가 보수적이다: 가장 무게가 큰 예측기의 자기 띠에 백테스트 오차를 제곱합으로 더하고, 정상 계열에도 랜덤 워크처럼 √h로 넓힌다. 정밀도 게이트와 ML 결정은 한 걸음 앞(h1, 84–89 %)만 쓰므로 그대로 두었다 — 좁히면 게이트가 잡는 관측이 20 %까지 늘어 동작이 바뀐다. | 포크 정렬 회전 | 고정 1.2 rad/s 제자리 회전 | 평소 회전과 같은 물리(스키드 피벗, 못 하면 크리프), 최대 1.2 rad/s | **[측정]** 기본 · wheel_lift · budget · 배터리 부족 프리셋의 바퀴 · 트랙은 모든 지면에서 1.2 그대로. budget 메카넘만 0.69 rad/s(옛 코드는 평소의 1.7배로 돌았음) |

되돌린 것: **목 45° 끝까지 숙이기**. 탑승자 확인 · 재확인에서 목이 45°(사람 굴곡 한계), 카메라 −57°까지 간다. 목을 25°(ISO 11226 허용 정적 자세)까지만 쓰고 나머지를 허리 · 엉덩이로 나누게 해 봤지만, ① 기본 바퀴 몸에는 허리 관절이 없어 탑승자는 달라지지 않고, ② 보행 몸은 발치의 원목을 보려고 엉덩이를 45° 숙여 오히려 부자연스러웠으며, ③ 대상을 화면 가운데에 두는 v1.1 · v1.2 사양을 지키려면 목 · 몸통이 그만큼 돌아야 한다. 탑승자에게 허리 피치가 있는 `wheel_lift`는 이미 허리로 나눈다.
